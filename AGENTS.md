# AGENTS.md

Guidance for AI coding agents working on wifiForce.

## Project

Single-file C++17 Win32 app (`main.cpp`) that forces Windows to keep Wi-Fi
connected while Ethernet is connected. GUI mode shows two buttons; `--watchdog`
mode runs headless as a SYSTEM scheduled task. The name is written `wifiForce`,
with a lowercase `w` - that casing is used in the file name, the window title,
the task names, the data folder and the documentation.

## Layout

- `main.cpp`: everything (embedded PowerShell scripts, helpers, watchdog, activate/restore, GUI)
- `app.manifest`: `requireAdministrator` + Common Controls 6
- `res.rc`: icon group (id 1), the manifest (`1 24`) and the version block
- `app.ico`: generated by `tools\make-icon.ps1`, committed because the build needs it
- `version.txt`: the only place the version lives
- `build.bat`: the build; bumps the version, writes `dist\wifiForce_v<version>.exe`
- `tools\version.ps1`: bump / keep / set the version (`-KeepVersion`, `-Version 2.0`)
- `tools\build-files.ps1`: writes `build\version_generated.h` and the manifest fix
- `tools\make-icon.ps1`: draws `app.ico` from geometry (Wi-Fi in a shield, JustViewMD's blue tile)
- `LICENSE`: Apache-2.0

## Build

```bat
build.bat                 rem release build, version bumped
build.bat --keep-version  rem rebuild the current version unchanged
build.bat --version 2.0   rem set the version outright
build.bat --clean         rem remove build\ first
```

The equivalent by hand, which needs the generated files from the first step:

```bash
powershell -File tools\build-files.ps1 -Version 1.0 -BuildDir build
windres res.rc -I build -I . -O coff -o build/res.o
g++ -O2 -std=c++17 -municode -mwindows -static -s -I build -specs=build/no-default-manifest.specs \
    main.cpp build/res.o -o build/wifiForce_v1.0.exe -lwlanapi -lole32
```

Requires MinGW-w64 (`winget install BrechtSanders.WinLibs.POSIX.UCRT`). A
`"UNICODE" redefined` warning is expected and harmless.

## Versioning

`version.txt` holds two numbers (`1.0`); a build that carries a change bumps the
last one. The major number moves only when the user asks for it by name. The
build writes that one number into the file properties, the window title and the
executable's name, so no copy can disagree. Never hard-code the version in
`main.cpp` or `res.rc`; include `version_generated.h` instead.

## The extra manifest (do not remove the specs file)

On a native Windows MinGW-w64 toolchain the compiler appends a `default-manifest.o`
to every link, and a cross-compiler on Linux does not. Linked together with the
app's own `requireAdministrator` manifest the executable ends up with two
`RT_MANIFEST` entries with the same id, the linker prints
`.rsrc merge failure: multiple non-default manifests`, and Windows may take the
`asInvoker` one - the app then silently runs unelevated and cannot write policy.
`tools\build-files.ps1` rebuilds the compiler's `endfile` spec without that
object and the build passes `-specs=`. Check a fresh binary with a resource
dump: there must be exactly one `24` entry.

## Architecture

- `Activate()`: write scripts to `%ProgramData%\wifiForce`, run `apply.ps1` (backs up, verifies the backup, then applies), check that `backup.json` exists, copy the exe to `wifiForceSvc.exe` (retried for 2 s), create tasks `wifiForceWatchdog` (ONSTART) and `wifiForceGuard` (every minute), run the watchdog.
- `Restore()`: delete tasks, kill `wifiForceSvc.exe`, run `restore.ps1`, and only when that exits 0 delete the files and the folder (each delete retried, folder removal verified). A failed restore keeps `backup.json` and the whole folder so it can simply be run again.
- Watchdog (`Watchdog`, `WlanTick`, `EnforceRegistry`): 3 s loop using the WLAN API. Single instance via mutex `Global\wifiForceWatchdogMutex`. Last-used profile is stored in `last.bin`.
- Active state = `backup.json` exists AND task `wifiForceWatchdog` exists (`IsActive`).

## Backup contents and exit codes

`backup.json` holds every value Activate touches: `reg` (policy values, with whether each existed), `adv` (driver options), `pm` (power management), `prof` (profile connection modes), `state` (each Wi-Fi adapter's on/off state) and `svc` (`WlanSvc` start type). Missing sections are tolerated, so an old backup still restores.

The scripts report what they did, and the GUI shows the error instead of a status:

| script | exit | meaning |
|---|---|---|
| `apply.ps1` | 0 | backup written and policy values in place |
| | 2 | the backup could not be written or read back - nothing was changed |
| | 3 | a policy value did not take |
| `restore.ps1` | 0 | everything restored, `backup.json` removed |
| | 3 | `backup.json` exists but cannot be read |
| | 4 | a policy value did not come back - backup kept for another try |
| | 5 | `backup.json` could not be removed |

## Conventions and gotchas

- The installed copy is named `wifiForceSvc.exe` so `taskkill /IM` never kills the GUI instance.
- Keep the PowerShell scripts ASCII-only; they are written with a UTF-8 BOM by `WriteText`.
- Never overwrite `backup.json` if it exists (re-Activate must not capture already-modified values as "originals").
- Do not parse localized `netsh` text for state. Profile connection mode is read from exported profile XML (`connectionMode`), which is locale-independent. Profile names are parsed from the indented lines of `netsh wlan show profiles`.
- Adapter options are matched by display name regex `disable.*(wired|ethernet|\blan\b)`. Extend carefully; a wrong match could change an unrelated driver setting.
- All long-running work happens on a worker thread; the UI thread only updates state via `WM_APP+1`. `IsActive()` spawns `schtasks`, so it runs on its own thread too and answers with `WM_APP+2` (`RefreshAsync`); never call it from the UI thread.
- Reconnect attempts are throttled (8 s), the PowerShell adapter-enable is throttled (60 s), and the watchdog restarts `WlanSvc` if it is stopped (20 s). Each throttle has its own timestamp; do not make them share one, or one action postpones the other.
- `Run()` terminates a child that passes its timeout and returns `(DWORD)-2`; the watchdog's `enable.ps1` call passes 30 s so a hung PowerShell cannot hold the 3 s loop up.
- The watchdog refuses to start when `backup.json` is missing: enforcing the policy without a record to restore from would be a change nobody can undo.
- One GUI instance at a time, held by `Local\wifiForceGuiMutex`; a second launch brings the existing window forward. Do not release the handle, or the name is free again.
- Never write to the network-adapter property that reports `Unsupported` for `AllowComputerToTurnOffDevice`; ask first, set only when it is supported.
- Do not restart `WcmSvc` in code; it briefly drops all networking.
- The scheduled tasks must allow starting on battery and have no execution time limit (set via `Set-ScheduledTask` after `schtasks /Create`, whose defaults would kill the watchdog on battery and after 72 h).
- Renaming anything the installed copy owns (task names, `%ProgramData%\wifiForce`, `wifiForceSvc.exe`) is safe only because Windows matches those case-insensitively; `Global\wifiForceWatchdogMutex` is case-sensitive, so an old and a new watchdog can run side by side for a moment. Both only rewrite the same values, so the overlap is harmless.

## Testing

This cannot be run on Linux. Cross-compile, then test on Windows 10/11 as administrator with a laptop that has both Wi-Fi and Ethernet:

1. Activate, plug in Ethernet, confirm Wi-Fi stays connected.
2. Disconnect Wi-Fi manually; it should reconnect within about 3 s.
3. End `wifiForceSvc.exe` in Task Manager; it should return within a minute.
4. Restore; confirm tasks, `C:\ProgramData\wifiForce` and the policy values are gone/reverted.

## Do not

- Add network calls or telemetry.
- Leave changes behind after Restore.
- Weaken the backup logic.
